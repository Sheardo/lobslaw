# lobslaw-retrieval-raft-only

**Decision:** All retrieval indexes and derived structures live in the Raft-replicated store. NO external vector database, NO pluggable VectorStore vtable, NO sidecar. This covers the lexical inverted index (BucketTermPostings / BucketDocStats), the vector band prefilter (BucketVectorBands), and the embedding outbox (BucketEmbedOutbox). Approximate vector search is implemented in-tree as a SimHash band prefilter whose band values are HMAC'd with the cluster MemoryKey and stored in the KEY space, so a prefilter lookup is a bbolt prefix seek that never opens a sealed payload. Anything that cannot be expressed as Raft-resident derived state is out of scope for retrieval. Every derived index must be built inside FSM.Apply for the record's own log entry — never via a second raft.Apply — and must be reproducible byte-identically from a snapshot on every replica.

## Rationale

Rejected the nullclaw approach (qdrant / pgvector / lancedb behind a vtable) for four reasons specific to lobslaw: an external store is a second unreplicated source of truth that can diverge from the FSM with no detection; it reintroduces a sidecar the project just removed (commit 5cf9725 dropped tools-runtime + uv sidecars); shipping embeddings to a network service is an egress and data-classification event in a product whose distinguishing feature is architecturally-controlled egress; and the deployment target is personal-scale hardware where an in-tree band prefilter is comfortably sufficient. MEASUREMENT that informed the design (internal/memory/search_bench_test.go, D=1536, first benchmark this path has ever had): the scan costs ~12.5us and ~13.9KB of allocation PER RECORD PER QUERY, so N=10000 is 125ms and 139MB per user message, and the code comment claiming "fine for personal scale (< ~100k records)" extrapolates to ~1.25s and ~1.4GB per turn. Layer breakdown at N=10000: secretbox decrypt ~71%, proto.Unmarshal ~20%, cosine arithmetic ~16%, redundant norm ~3%, sort-all ~1%. The arithmetic the algorithm needs is its smallest component, so the prefilter must be designed to avoid the DECRYPT rather than the maths — which is why bands go in the key space rather than inside the sealed record. HMAC on the band value closes a leak the obvious implementation would open: bbolt keys are not sealed, and a raw SimHash band is a coarse content fingerprint that would let someone with the file but not the key learn which records are semantically similar. Banding needs equality and never ordering, so HMAC costs nothing. Store.ForEachPrefix is the existing in-tree precedent for exactly this move. Full design in ROADMAP.md Retrieval section (R6, R20, R21).
