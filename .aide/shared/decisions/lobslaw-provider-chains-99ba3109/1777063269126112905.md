# lobslaw-provider-chains

**Decision:** Provider chains are now expressed via per-provider .backup pointer on ProviderConfig instead of a separate [[compute.chains]] block. At runtime the agent walks backup pointers on hard failures (5xx, rate-limit, timeout, connection refused) producing same-turn transparent fallback. Cycle detection at config load via validateProviderBackups; unknown backup labels are rejected. ProviderRegistry (compute.ProviderRegistry) surfaces label → client + metadata for introspection and chain-walking. Previous ChainConfig / ChainStepConfig / ChainTriggerConfig types retained for back-compat but deprecated — new deployments use .backup.

## Rationale

User asked for a simpler chain expression: 'one provider has another as its backup, chain emerges'. Per-provider backup is more operator-obvious than a separate chain block and makes the 'when primary fails, use secondary' intent co-located with the primary's own config. Cycle detection required because a→b→a loops are easy to write by accident. Provider registry unifies both council_review fan-out and backup-chain walks over the same label lookup infrastructure.
