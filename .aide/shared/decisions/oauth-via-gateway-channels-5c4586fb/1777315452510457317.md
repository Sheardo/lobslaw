# oauth-via-gateway-channels

**Decision:** OAuth device-code flows can be initiated via any gateway channel (Telegram, REST, future channels). Owner messages 'connect google workspace' (or /oauth google scope1 scope2); agent calls oauth_start(provider, scopes) builtin; response shows the verification URL + user_code; backend service polls the provider's token endpoint until success or expiry. On success, refresh token is encrypted (cluster MemoryKey) and stored in BucketCredentials with an EMPTY AllowedSkills array — operator must explicitly grant per-skill access via credentials_grant(skill, provider, scopes). All five oauth/credentials builtins (oauth_start, oauth_status, oauth_revoke, credentials_grant, credentials_revoke) are default-deny at the policy seed; subject='scope:owner' allow rule (the same pattern used for soul_*) opens them.

## Rationale

Device-code flow works without a callback URL — fits cluster deployments with no public ingress. Owner can connect new providers from their phone; CLI flow stays as headless backup. Empty default ACL means freshly-connected credentials are inert until operator explicitly grants — no implicit privilege escalation. Reusing the scope:owner policy pattern keeps the trust model uniform with existing soul tools.
