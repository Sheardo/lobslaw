# lobslaw-skill-storage-model

**Decision:** Cluster store (Raft+bbolt) is authoritative for skills. The filesystem becomes two separate things: an import/export interchange format, and a disposable per-node execution cache. Buckets: BucketSkills (imported signed+operator tiers), BucketSelfTaught (agent-authored), BucketSkillVersions (history), BucketSkillBlobs (small text payloads). Manifest bytes are stored VERBATIM alongside the detached ed25519 signature, because signing.go verifies a signature over the exact manifest file: parsing and re-serialising would break verification permanently and make SigningRequired reject genuinely signed skills. Large or binary payloads stay in the storage layer, content-addressed by a digest held on the record. Materialisation to a per-node cache is mandatory, not a compromise: invoker.buildPolicy grants Landlock Read+Exec on skill.ManifestDir, so the store cannot be exec'd. The cache is disposable and rebuilt on boot, record change, digest mismatch, or explicit command; Registry.Scan/Watch are unchanged and simply point at it. candidateBeats reorders to tier-first (signed > operator > agent) then version. A configured dev directory retains live edit-and-reload, always wins locally, and is never written to the store or replicated. SUPERSEDES the "skills live in storage as directories" clause of lobslaw-skills and lobslaw-persistence-model.

## Rationale

One source of truth rather than two authorities needing a reconciliation rule between them. Versioning, rollback, backup and restore fall out of the store instead of each needing a filesystem convention (soul_history_rollback is the existing precedent for the CLI shape). Closes the DEFERRED.md cross-cluster-storage-tunneling gap for skills: every node has every skill because every node has the log, so a compute-only node no longer depends on a peer materialising a mount. Surfaces and fixes a latent privilege-escalation path: candidateBeats currently orders version before preferSigned, so an unsigned v2 beats a signed v1 — harmless while only operators can author skills, exploitable the moment an agent can bump a version to take a name. Provenance-by-location survives via separate buckets, so self_learning.mode=off remains verifiable by absence rather than by a branch. REJECTED ALTERNATIVES: filesystem-authoritative status quo (a skill exists only where a mount is materialised; no version history); split authority with agent skills in the store and signed/operator on disk (two sources of truth plus arbitration — this was the earlier ROADMAP R15 draft); store-only with no filesystem at all (execution requires Landlock Read+Exec on a real directory); filesystem plus a directory-replication daemon (reimplements Raft badly, no version history, split-brain on concurrent edits). OPEN QUESTIONS to settle before implementation: (1) blob size threshold, and whether reference files above it are permitted at all; (2) whether a live-watched operator directory is legal in production or strictly development-only; (3) version history is unbounded and inflates every Raft snapshot forever — needs keep_versions=N plus GC, or versioned skills becomes a store-growth problem. Depends on ROADMAP R0 (leader forwarding), since skills install becomes a Raft write. Full design in ROADMAP.md R18.
