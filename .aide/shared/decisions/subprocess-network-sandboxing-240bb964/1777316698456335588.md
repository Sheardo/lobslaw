# subprocess-network-sandboxing

**Decision:** When process sandboxing is enabled for a subprocess (skill, future binary-installed tool), the sandbox installs nftables rules INSIDE THE SUBPROCESS'S OWN NETWORK NAMESPACE that DNAT outbound TCP 80/443 to the lobslaw egress proxy. CRITICAL: the rules MUST be scoped to the subprocess's netns ONLY — never to the host namespace where lobslaw + the embedded smokescreen goroutine live, which would create an infinite redirect loop. Smokescreen runs IN-PROCESS in lobslaw's host namespace; subprocess netns is separate; no self-redirect possible. DNS UDP 53 is exempted from the redirect (otherwise lookups fail) — skills resolve via the netns's stub resolver, then connect via the redirected TCP. Configurable via policy: subjects covered by 'sandbox.network=enforce' get the netns+nftables treatment; subjects covered by 'sandbox.network=permissive' get HTTPS_PROXY env only (honest-process trust). Default-enforce for skill subprocesses; default-permissive for legacy paths. Linux-only — non-Linux deployments fall back to permissive with a one-time WARN at boot, same pattern as shell_command Landlock fallback. The path from netns to smokescreen is via either a veth pair (host endpoint = smokescreen's listen IP) or a unix socket bind-mounted into the netns; choice deferred until E.5 implementation.

## Rationale

HTTPS_PROXY env is honour-based; a malicious binary that ignores it gets unfettered network access. nftables redirect is the kernel-enforced fallback — defence-in-depth on top of HTTPS_PROXY. Tying it to the existing process-sandbox policy means operators get one switch ('sandbox enabled') rather than separate FS-vs-network toggles. The netns scoping is what prevents lobslaw redirecting its own egress back into itself; that scoping is non-negotiable and noted as CRITICAL in this record so it doesn't get lost in implementation.
