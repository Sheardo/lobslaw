# subprocess-network-sandboxing

**Decision:** When process sandboxing is enabled for a subprocess (skill, future binary-installed tool), the sandbox installs nftables rules in the subprocess's network namespace that DNAT all outbound traffic to the lobslaw egress proxy UDS. This catches malicious subprocesses that ignore HTTPS_PROXY env or use raw sockets — kernel-enforced redirect happens regardless of what the binary thinks it's doing. Configurable via policy: subjects covered by a 'sandbox.network=enforce' rule get the netns+nftables treatment; subjects covered by 'sandbox.network=permissive' get HTTPS_PROXY env only (honest-process trust). Default-enforce for skill subprocesses; default-permissive for legacy paths. Linux-only — non-Linux deployments fall back to permissive with a one-time WARN at boot, same pattern as shell_command Landlock fallback.

## Rationale

HTTPS_PROXY env is honour-based; a malicious binary that ignores it gets unfettered network access. nftables redirect is the kernel-enforced fallback — defence-in-depth on top of HTTPS_PROXY. Tying it to the existing process-sandbox policy means operators get one switch ('sandbox enabled') rather than separate FS-vs-network toggles. Linux-only is acceptable because that's where lobslaw production runs; non-Linux dev still gets the in-process Go-side filtering.
