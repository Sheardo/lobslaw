# lobslaw-durable-writes-go-through-raft

**Decision:** Anything that must survive a restart is PROPOSED THROUGH RAFT. Writing to state.db directly is not a shortcut to the same result: the node rebuilds its state from the raft log on boot, so a direct PUT is overwritten by whatever the log says and a direct DELETE is RESURRECTED. The asymmetry is the trap — a tool that writes and deletes directly appears to half-work, because its writes are re-applied by later log entries carrying the same content while its deletions silently come back. This is why lobslaw memory reembed is an RPC against a running node rather than an offline pass over the file, and why the offline cmd/backfill-embeddings is documented as being for a cluster that will not start at all, with its limitation stated rather than implied. The same rule applies to any future repair tool: if the change must persist, it goes through raft, and if it cannot, the tool says so where an operator will read it.

## Rationale

Learned twice in one week at the cost of a wrong conclusion each time. First: backfill-embeddings appeared to complete a model migration, and the next boot had both old and new vectors, because its deletions did not survive replay. Second: the fix for that was itself written as a direct-store pass before the same failure recurred, so the repair became a raft-proposed RPC (memory.Reembed). The rule is implied by lobslaw-persistence-model — memory is the raft-replicated layer — but 'memory lives in raft' does not tell you what happens when you write underneath it, and that gap is where both hours went. Stating the failure mode is the point: the danger is not that direct writes fail loudly, it is that they succeed convincingly until the next restart.

## Details

Landed as internal/memory/reembed.go (Reembed proposes every vector write and delete through raft) and the docs note in docs/docs/features/memory.md. Related trap recorded in the same area: a repair that runs through raft must still not delete what it cannot rebuild — Reembed guards dream's consolidations by keying superseded vectors on len(SourceIds)==1, after an earlier version destroyed 20 consolidations by keying on each source in turn.
