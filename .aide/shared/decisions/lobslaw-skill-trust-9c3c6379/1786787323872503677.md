# lobslaw-skill-trust

**Decision:** Skill trust model is clawhub-compatible by default: trust-on-install-after-operator-review. Install flow displays manifest + source tree; operator approves. AMENDED 2026-08-15: the approval/re-approval lifecycle is now specified by lobslaw-skill-approval-lifecycle — approval fires at activation, verification runs at materialisation and invoke, and the recorded digest is a root over manifest + handler + reference files + declared binary digests (the original "SHA-256 of the manifest+handler tree" understated what must be covered, and the shipped code only digests the manifest file). The "registry changes trigger re-approval" clause is superseded: re-approval is triggered by a change in the approved digest set, not by a registry rescan. Optional hardening via skills.require_signed=true enables ed25519 verification against a local trusted_publishers file. Skills declaring sidecar:true or wildcard security.fs/network always trigger explicit operator confirmation regardless of signing status.

## Rationale

ClawHub itself does not sign skills — its trust is social (GitHub-age + reporting + moderation). Matching that keeps clawhub sync working. Adding a digest pin per approval gives trust-on-first-use semantics as a defence-in-depth layer. Optional signing for the paranoid without forcing ceremony on casual users. AMENDED 2026-08-15 for two reasons. First, lobslaw-skill-storage-model makes the registry store-authoritative, so a filesystem-change trigger no longer exists. Second, a review found the shipped digest is narrower than this decision claimed: the ed25519 signature covers only the manifest bytes, Skill.SHA256 is the manifest-file digest, and the handler script — the code that actually executes — is neither signed nor pinned. Swapping the handler while leaving the manifest untouched passes every current check. That gap is tracked as ROADMAP R19 and is independent of the storage move.
