# credential-storage

**Decision:** Credentials live in a new Raft bucket (BucketCredentials). Record shape: ID (ULID), Provider (google/github/...), Subject (user@example.com), AccessToken+RefreshToken (both encrypted with cluster MemoryKey at rest, NEVER decrypted into the agent's context), Scopes, ExpiresAt, AllowedSkills, AllowedScopesPerSkill, audit timestamps. Skill-side flow: skill subprocess calls credentials_request(provider, scopes); handler verifies caller is in AllowedSkills + scopes ⊆ AllowedScopesPerSkill[caller]; if access token is fresh, decrypt+return; else refresh via provider's /token endpoint (through smokescreen with role 'lobslaw:credentials:<provider>' — locked-down ACL to just the IdP token endpoint) and update record. Token reaches the skill subprocess via env or stdin; agent's context never sees raw token bytes.

## Rationale

Operator approval is the trust root: only the operator (via CLI or Telegram-as-owner) can grant a skill access to a credential. Agent can't read raw refresh tokens. Encryption at rest with the existing cluster MemoryKey reuses the encryption infrastructure already in place for state.db value encryption. Per-skill scope subsetting prevents scope creep — gws-workspace can't quietly broaden from gmail.readonly to gmail.send.
