# lobslaw-skills

**Decision:** Skills registry with clawhub.ai-compatible manifest (OpenClaw manifest format). AMENDED 2026-08-15: skills are records in the cluster store per lobslaw-skill-storage-model. A directory containing manifest.yaml + handler + optional SKILL.md/SOUL.md is no longer where a skill lives — it is the import/export interchange format, and the shape of the disposable per-node execution cache the registry scans. Trust model per lobslaw-skill-trust (trust-on-install-after-operator-review, optional minisign); manifest bytes are stored verbatim with their detached signature so verification is unaffected by the move. Invocation format compatible with OpenClaw so clawhub sync works unchanged. Skills can be shipped inside lobslaw plugin directories (see lobslaw-plugins) alongside hooks and MCP server declarations; those directories are imported rather than watched in place.

## Rationale

Original decision named the registry feature set. Expanded to: trust model explicit (see lobslaw-skill-trust), plugin directory format explicit (see lobslaw-plugins), and OpenClaw compatibility preserved. Skills are one of several artefacts a plugin can ship, not the only one. AMENDED 2026-08-15: the "skills live in storage as directories" clause is superseded by lobslaw-skill-storage-model. Directories remain the interchange format precisely so clawhub compatibility and the plugin directory layout survive the change — nothing about the manifest format, invocation contract, or trust model changes, only where authority sits. Note for lobslaw-skill-trust: its "registry changes trigger re-approval" clause needs re-reading under the new model, since the registry no longer changes by filesystem edit; whether re-approval fires on import, materialisation, or activation is unresolved.
