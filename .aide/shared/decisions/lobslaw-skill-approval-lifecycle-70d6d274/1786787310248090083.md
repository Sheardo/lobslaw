# lobslaw-skill-approval-lifecycle

**Decision:** Skill approval and skill verification are separate mechanisms with different triggers. APPROVAL is a human trust act, fires ONCE at ACTIVATION (the transition that makes a skill selectable by the agent), and records {approved_root, approved_by, approved_at, tier}. VERIFICATION is a mechanical digest check with no human in the loop, and runs at materialisation and again before invoke; a mismatch refuses the skill and revokes its approval. The approved_root is a digest over name + version + manifest digest + handler digest + every reference file digest + declared binary digests — the files map on the R18 SkillRecord makes this near-free. Re-approval is triggered by a CHANGE IN THE APPROVED DIGEST SET, not by a registry rescan. Activation-time approval is the same gate as self_learning propose mode, so clawhub skills and agent-authored skills share one approval path and one prompt surface. Confirmation-on-first-invoke is retained as an ADDITIONAL gate for the agent tier only, not as the primary one. Supersedes the "registry changes trigger re-approval" clause of lobslaw-skill-trust.

## Rationale

The old clause does not parse under lobslaw-skill-storage-model because "registry changes" named a filesystem event, and under a store-authoritative model the registry no longer changes by filesystem edit. Rejected triggers: ON IMPORT is too early — in propose mode the operator would approve artefacts that may never activate, and the prompt arrives detached from any intent to use the skill. ON MATERIALISATION is actively wrong — materialisation is derived, automatic and idempotent, firing on boot, on digest mismatch, on rematerialise and on any node, so gating it means an approval prompt can appear on node restart. ON FIRST INVOKE ALONE is too late for the general case: by then the skill is loaded and its policy.d tool policies are registered. Activation is the last point at which nothing has been selected or executed but the operator intent to use the skill is clear. Separating approval from verification also fixes the re-approval semantics: a rescan of unchanged content is not a trust event, and treating it as one would prompt on every restart. IMPLEMENTATION GAP FOUND WHILE REVIEWING (independent of this decision and exploitable today): the handler script is neither signed nor pinned. The detached ed25519 signature covers only the manifest bytes, Skill.SHA256 is the manifest-file digest only, Manifest.Handler is a relative path, and the manifest SHA256 field belongs to binary declarations. An attacker who swaps the handler and leaves the manifest untouched passes both signature verification and the digest check. Tracked as ROADMAP R19. Full design in ROADMAP.md; see also lobslaw-skill-storage-model.
